## Additional findings

- **Deleting the visible card leaves a stale selection.** Draw a custom card, delete it in My Cards, then return to Play. The lookup falls back to the welcome prompt, but the stored type still enables Next Card and drives its next draw. The UI should consistently represent either an active turn or an empty card. [index.tsx:9–16](src/app/index.tsx#L9-L16), [index.tsx:63–86](src/app/index.tsx#L63-L86).
- **One bad stored record blocks the entire custom deck.** Invalid JSON, a non-array payload, or any invalid card sends the provider into a load-failed state. This protects the stored payload from being overwritten. A restart can recover from a transient read failure, but it repeats the same failure for a persistent malformed payload. The validator also accepts empty IDs and duplicate IDs, which can make React row identity, Play lookup, or deletion ambiguous for malformed data. [custom-cards.tsx:19–28](src/game/custom-cards.tsx#L19-L28), [custom-cards.tsx:37–58](src/game/custom-cards.tsx#L37-L58), [custom-cards.tsx:81–83](src/game/custom-cards.tsx#L81-L83), [my-cards.tsx:75–90](src/app/my-cards.tsx#L75-L90), [index.tsx:14–16](src/app/index.tsx#L14-L16).
- **The repeat rule protects identity.** Two saved copies of the same text, or a custom copy of a built-in, can be drawn consecutively. A Truth → Dare → Truth sequence can also return to the earlier Truth because the ref tracks the last draw globally. The latter matches a literal consecutive-draw rule. Duplicate content is the player-visible edge case. [cards.ts:99–103](src/game/cards.ts#L99-L103), [index.tsx:9–11](src/app/index.tsx#L9-L11), [index.tsx:41–45](src/app/index.tsx#L41-L45), [custom-cards.tsx:73–79](src/game/custom-cards.tsx#L73-L79).
- **Storage feedback can be easy to miss.** Delete failures use the error text at the top form, which can be far above the row the user tapped. During a write, the text fields and Add/Delete controls are disabled, but mode and card type can still change and a successful save resets them. Whitespace is handled. There is no length limit, and a large paste can grow the form, the drawn card, and the serialized payload substantially. The screen eagerly renders every saved card and each write serializes the whole list. That is straightforward for a small homework deck. [my-cards.tsx:21–35](src/app/my-cards.tsx#L21-L35), [my-cards.tsx:42–100](src/app/my-cards.tsx#L42-L100), [custom-cards.tsx:57–82](src/game/custom-cards.tsx#L57-L82).
- **VoiceOver needs a focused check.** Buttons expose role and selection state, and inputs have accessible labels. The changing question and form error use `accessibilityLiveRegion`, which React Native documents for Android. The implementation provides no explicit iOS announcement for these updates. Chinese text has no `accessibilityLanguage` hint, and every saved row exposes the same Delete label. Verify pronunciation, newly drawn card announcements, and whether users can identify which card they are deleting. [index.tsx:63–71](src/app/index.tsx#L63-L71), [my-cards.tsx:42–63](src/app/my-cards.tsx#L42-L63), [my-cards.tsx:75–97](src/app/my-cards.tsx#L75-L97), [ui.tsx:44–64](src/game/ui.tsx#L44-L64), [React Native accessibility](https://reactnative.dev/docs/accessibility).
- **SDK compatibility is supported by the dependency and documentation checks.** The installed Expo SDK 58 compatibility map agrees with the declared React Native, Expo Router, AsyncStorage, and safe-area-context versions. Expo documents AsyncStorage 2.2.0 as included in Expo Go. The Router setup uses the documented JavaScript tabs API. Keyboard inset adjustment is iOS-specific, so Android keyboard behavior still needs separate verification if tested. [package.json:4–27](package.json#L4-L27), [_layout.tsx:1–30](src/app/_layout.tsx#L1-L30), [ui.tsx:16–25](src/game/ui.tsx#L16-L25), [Expo SDK 58](https://docs.expo.dev/versions/v58.0.0/), [Expo SDK 58 AsyncStorage](https://docs.expo.dev/versions/v58.0.0/sdk/async-storage/), [Expo Router JavaScript tabs](https://docs.expo.dev/router/advanced/tabs/), [React Native ScrollView](https://reactnative.dev/docs/scrollview#automaticallyadjustkeyboardinsets).
- **Code structure is proportionate to the assignment.** The routes share the picker, buttons, and page shell. One provider owns custom-card state, serializes writes with an in-flight guard, and updates the UI after a successful write. Repeated blank-input validation is justified at the form and storage boundaries. The actionable cleanup is the lint-failing starter hook. The draw-time filters and whole-list rendering are simple at the expected deck size. ## Prioritized follow-up

1. **Verify iPhone persistence and interaction.** Force-quit after a confirmed add and after a confirmed delete. Check rapid draws, switching tabs with an unfinished draft, and the English and Chinese keyboards with long input.
2. **Resolve the stale Play selection after deletion and restore a clean lint run.** Cover the exact draw → delete → return flow so the card and Next Card agree about the current turn.
3. **Improve recoverability and accessibility.** Make delete errors discoverable near the affected row, provide a recovery path for unreadable saved data, and test VoiceOver announcements, Chinese pronunciation, and contextual Delete labels.
4. **Address duplicates and very long input if they affect play.** Decide whether identical bilingual text counts as a repeat, and set a practical length limit if device testing shows that long cards make controls difficult to reach.

## Conclusion

The built-in deck and draw logic check out, and the custom-card and tab flows are traceable from the source. The force-quit, keyboard, and layout checks are the main open acceptance items. The delete-selection inconsistency is the first gameplay fix worth making.
